## What it does

<!-- Stable description of the program. Carried forward from the previous note; edit only when the product itself changes.
     3 to 6 lines: what it is, who uses it, where it runs (URL/port/binary), how to start it. -->
heaptide finds leaks in CPU, GPU (HIP and Mojo) and Python programs in one pass, without
rebuilding them. On an 8-thread malloc benchmark it runs 12x faster than heaptrack with 6.7x less
added memory. On every planted leak in its test suite, its direct/indirect split matches
LeakSanitizer's. It also sees HIP device and pinned host memory, Mojo's GPU buffers included,
which no other leak tool we know of covers on ROCm.

```
heaptide run [--gpu] [--py] [--py-depth N] [--every MS] [--snapshot-every S] [--out DIR] -- CMD...
heaptide snapshot DIR
heaptide report DIR [--json] [--top N] [--supp FILE] [--fail-on any|leaks|growth|none]
heaptide attach PID [--out DIR]  ·  heaptide detach DIR  ·  heaptide diff BASE NEW
```

## Highlights

<!-- 1 to 5 bullets a user would notice. Lead with the benefit, not the implementation. -->
- `--py` reports name `py::` functions on any machine: the perf map is copied into the report dir.
- `diff` finds a GROWN site even past `--top`, and matches sites across builds without LLVM (GNU `addr2line`).
- A clean HIP program shows no leak: the runtime's one-time setup is in the default suppressions.
- A stack overflow in a thread that never allocated still writes a report; short-lived threads no longer pile up signal stacks.

## Changes

### Added
- `report/addr2sym.sh`: names frames with GNU `addr2line` (one call per module) when llvm-symbolizer is missing; shipped in the tarball.
### Changed
- `diff` compares every leak site and every site whose peak passed 64 KiB, whatever `--top` is.
- `report/default.supp` drops the HIP runtime's one-time setup (216 B direct, 48 B indirect, 376 B under Mojo).
### Fixed
- `--py`: `/tmp/perf-<pid>.map` is copied into the report dir as `perf.<pid>.map` and read first.
- `pthread_create` is hooked: every thread gets its 64 KiB signal stack at start, not at its first allocation.
- That stack is unmapped when the thread exits (3000 short threads: VmSize +274020 KiB, now +82004 KiB; bare +81924).
